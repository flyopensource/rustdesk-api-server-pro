# 设备组策略模型调整方案

## 1. 文档状态

- 状态：已按本方案实施，真实设备和部署环境联调仍待完成
- 范围：RustDesk API Server Pro 管理端、策略解析和 Web 设备管理页面
- 客户端范围：原则上保持现有策略协议，不在本阶段改变客户端策略包结构
- 核心目标：将“设备组”定义为一套完整、可直接下发的设备运行策略

## 2. 背景与现状

当前管理端把同一台设备的配置拆在三个入口中：

1. “服务器配置”维护 ID Server、Relay Server、Server Key 和固定密码。
2. “设备组”只维护组名、启用状态和服务器配置引用。
3. “无人值守”在单台设备上单独维护，并带有 Root 执行器。

服务器配置还支持“单设备配置 → 已启用设备组 → 全局默认”的覆盖顺序。因此，一台设备可能同时出现以下状态：

- 属于 A 设备组；
- 使用单设备指定的 B 服务器配置；
- 无人值守开关来自设备自身；
- 固定密码又来自 B 服务器配置。

这种结构虽然能组合出很多结果，但管理员无法通过“所属设备组”直接判断设备最终会获得什么策略，Web 页面也必须同时提供设备组、服务器配置和无人值守三个操作入口。

## 3. 调整目标

调整后的业务定义如下：

> 服务器配置是可复用的网络连接参数；设备组是一套完整的设备运行策略。

设备组的核心策略由以下三部分组成：

1. 服务器配置；
2. 是否开启无人值守；
3. 固定密码。

设备只需要选择所属设备组，不再分别选择服务器配置或单独编辑无人值守策略。

## 4. 非目标

本次调整不包含以下内容：

- 不改变 `rud.cfg` 只提供固定 provisioning API Server 的启动引导方式。
- 不让服务器配置中的 ID Server、Relay Server 或 Server Key 覆盖固定的 provisioning API Server。
- 不改变现有策略信封的签名、加密、防重放和目标设备校验机制。
- 不改变设备实际权限、Root、屏幕采集、无障碍和服务状态的上报字段。
- 不在设备组内引入逐字段继承或逐字段覆盖。
- 不把固定密码明文返回给 Web 管理端。
- 不迁移或兼容旧的服务器配置密码、单设备策略和全局服务器配置数据。

## 5. 调整后的对象职责

### 5.1 服务器配置 `ServerProfile`

服务器配置只描述 RustDesk 服务端连接信息：

| 字段 | 说明 |
| --- | --- |
| `id` | 配置 ID |
| `name` | 配置名称 |
| `id_server` | ID Server 地址 |
| `relay_server` | Relay Server 地址，可为空 |
| `server_key` | Server Key，可为空 |
| `enabled` | 是否允许被设备组选择 |

以下内容不再属于服务器配置：

- 固定密码；
- 无人值守开关；
- Root 执行器；
- 单设备或全局应用关系。

同一份服务器配置可以被多个设备组复用，各组可以使用不同的无人值守策略和固定密码。

### 5.2 设备组 `DeviceGroup`

设备组代表完整的下发策略：

| 字段 | 说明 |
| --- | --- |
| `id` | 设备组 ID |
| `name` | 设备组名称 |
| `enabled` | 设备组是否可用 |
| `profile_id` | 关联的服务器配置 |
| `unattended_enabled` | 是否开启无人值守 |
| `password_ciphertext` | 加密保存的固定密码 |
| `root_command` | 无人值守内部执行器，默认 `auto` |

`root_command` 属于无人值守的技术子配置，不作为普通管理员必须理解的第四个业务维度。Web 默认使用 `auto`；如果以后确实需要适配不同 Root 环境，可以放在“高级设置”中编辑。

### 5.3 设备 `Device`

设备只保留策略归属和策略执行结果：

- `strategy_group_id`：所属设备组；
- 当前策略版本与已应用版本；
- 当前服务器配置来源和连接状态；
- 无人值守、Root、权限和服务运行状态；
- 最近上报时间和错误。

以下单设备策略字段停止作为有效配置来源：

- `strategy_profile_id`；
- `unattended_enabled`；
- `root_command`。

实现时直接删除这些旧配置字段及对应逻辑，不保留过渡读取和回滚兼容分支。

### 5.4 默认设备组

原来的“全局默认服务器配置”调整为“默认设备组”。

未明确分组的设备使用默认设备组的完整策略，而不是只继承一份服务器配置。默认设备组同样包含服务器配置、无人值守开关和固定密码。

默认关系在系统内全局唯一，Web 在设备组编辑表单中以“默认设备组”开关维护。开启新默认组会自动取消原默认组；关闭开关后允许系统暂时没有默认组。

建议将 `StrategyState.GlobalProfileId` 调整为 `DefaultGroupId`。

## 6. 策略生效规则

策略解析只允许整套选择，不进行字段混合。

生效顺序：

1. 设备已分配到一个启用的设备组：使用该设备组完整策略；
2. 设备真正未分组（`group_id = 0`）：使用启用的默认设备组；
3. 设备已分组但该组或关联服务器配置不可用：不回退默认组，返回无管理策略并告警；
4. 未分组设备没有可用的默认组：不启用隐藏服务器配置，无人值守关闭，管理端固定密码清空。

### 6.1 原子性要求

一次策略解析必须从同一个设备组得到：

- 服务器配置引用；
- 无人值守开关；
- 固定密码；
- Root 执行器。

禁止出现“服务器配置来自单设备、无人值守来自设备组、密码来自全局”等混合结果。

### 6.2 设备组停用

- 已停用设备组不能再分配给设备。
- 已属于该组的设备保留分组关系，便于管理员恢复。
- 策略解析时保留所属组关系，但返回无管理策略，不回退默认设备组。
- Web 必须显示“所属组已停用，当前无可用策略”，不能只显示原组名称。

### 6.3 服务器配置停用

- 已停用服务器配置不能再被新建或编辑后的设备组选择。
- 已引用该配置的设备组不应静默拼接其他配置。
- 将该设备组判定为不可用，已属于该组的设备返回无管理策略，不回退默认组。
- Web 应明确显示“关联服务器配置已停用”。

## 7. 无人值守与固定密码规则

固定密码归设备组所有，并继续使用现有 provisioning 密钥加密保存。

建议采用以下明确行为：

| 无人值守 | 组内是否设置密码 | 实际下发 |
| --- | --- | --- |
| 开启 | 已设置 | 下发组固定密码 |
| 开启 | 未设置 | 下发空密码，并在 Web 提示配置不完整 |
| 关闭 | 已设置 | 服务端保留密文，但向客户端下发空密码 |
| 关闭 | 未设置 | 下发空密码 |

这样关闭无人值守时，不会继续保留一份由管理端提供的可用固定密码；重新开启后再从设备组恢复下发。

密码管理要求：

- Web 查询只返回 `password_set`，不返回明文或密文。
- 编辑时留空表示保持原密码不变。
- 使用独立“清除密码”操作明确删除密码。
- 修改或清除密码必须提升策略版本。
- 日志、审计、错误响应和测试快照不得记录密码明文。
- 修改一个设备组密码会影响该组全部设备，Web 保存前应显示影响设备数量。

## 8. Web 管理页面调整

### 8.1 服务器配置弹窗

保留以下字段：

- 配置名称；
- ID Server；
- Relay Server；
- Server Key；
- 启用状态。

移除固定密码输入、密码已设置状态和清除密码开关。

列表中显示被多少个设备组引用，不再统计单设备直接引用数量。

### 8.2 设备组管理弹窗

设备组表单包含：

- 组名；
- 服务器配置，必选；
- 开启无人值守；
- 固定密码；
- 清除固定密码；
- 设备组启用状态；
- Root 执行器高级设置，默认折叠且使用 `auto`。

设备组列表至少显示：

- 组名；
- 服务器配置名称；
- 无人值守开启/关闭；
- 固定密码已设置/未设置；
- 成员设备数量；
- 设备组状态。

为避免两个“启用”混淆，界面文案必须分别使用：

- `设备组状态：启用/停用`；
- `无人值守：开启/关闭`。

### 8.3 设备列表

设备列表只保留“所属设备组”作为策略编辑入口。

移除：

- 单设备服务器配置下拉框；
- 单设备无人值守编辑按钮。

保留只读展示：

- 生效设备组；
- 生效服务器配置；
- 无人值守状态；
- 固定密码是否已配置；
- 目标策略版本/已应用版本；
- 客户端实际连接来源与连接状态；
- 权限、服务和错误状态。

删除页面顶部独立的默认组下拉框，在设备组编辑表单内增加“默认设备组”开关。已停用的组不允许设为默认；停用当前默认组时同一事务清除默认关系。

### 8.4 特殊设备

第一阶段不提供单设备逐字段覆盖。特殊设备需要不同策略时，为其创建独立设备组。

如果未来确实需要单设备例外，只允许覆盖完整策略包，不允许分别覆盖服务器配置、无人值守或固定密码，否则会重新产生当前的混合来源问题。

## 9. 服务端数据模型调整

建议的数据结构变化：

### 9.1 `strategy_server_profile`

- 保留 ID Server、Relay Server、Server Key 等现有字段。
- 删除 `password_ciphertext`。
- 不迁移该字段已有数据。

### 9.2 `strategy_device_group`

新增：

- `unattended_enabled tinyint not null default 0`；
- `password_ciphertext text`；
- `root_command varchar(255) not null default 'auto'`。

保留：

- `profile_id`；
- `enabled`；
- 名称和时间字段。

### 9.3 `strategy_state`

- 使用 `default_group_id` 替换 `global_profile_id`。
- 不转换原全局服务器配置关系。

### 9.4 `device`

- `strategy_group_id` 继续作为设备的策略入口。
- 删除 `strategy_profile_id`、`unattended_enabled` 和 `root_command` 配置字段。
- 已应用版本和运行状态字段继续保留。

## 10. API 调整

### 10.1 服务器配置接口

服务器配置新增/更新请求删除：

- `permanent_password`。

响应删除：

- `password_set`；
- 单设备直接引用数量。

保留配置是否被设备组引用的校验，仍禁止直接删除正在使用的服务器配置。

### 10.2 设备组接口

设备组新增/更新请求增加：

```json
{
  "name": "自助售货机-A组",
  "enabled": true,
  "profile_id": 1,
  "unattended_enabled": true,
  "permanent_password": "仅新增或替换时提交",
  "clear_password": false,
  "root_command": "auto"
}
```

设备组查询响应增加：

- `profile_name`；
- `unattended_enabled`；
- `password_set`；
- `root_command`；
- `member_count`；
- 配置完整性状态。

服务端不能在查询响应中返回 `permanent_password` 或 `password_ciphertext`。

### 10.3 设备接口

保留设备分组接口。

删除以下旧接口：

- 单设备服务器配置接口；
- 单设备无人值守接口；
- 全局服务器配置接口。

默认开关作为设备组新建/更新请求的 `is_default` 字段，与组策略在同一事务中保存，一次操作只提升一次策略版本。

### 10.4 生效策略预览

预览接口以设备组为来源返回最终生效值，并增加：

- `group_id`；
- `group_name`；
- `group_source`，值为 `assigned`、`default` 或 `none`；
- `group_warning`，用于显示所属组停用、服务器配置停用或默认组不可用等原因。

## 11. 客户端兼容性

现有客户端策略包已经分别包含：

- `android.unattended.enabled`；
- `android.unattended.root_command`；
- `server_profile.id_server`；
- `server_profile.relay_server`；
- `server_profile.key`；
- `server_profile.permanent_password`。

因此服务端可以先完成数据归属和解析调整，再把设备组解析结果填入现有扁平策略包。正常情况下不需要修改客户端协议、签名或解密代码。

客户端继续执行：

- 策略验签、解密和目标设备校验；
- 保存策略版本；
- 更新隐藏服务器配置；
- 在服务器配置变化时重连 rendezvous；
- 应用无人值守状态并上报实际结果。

### 11.1 本机手工配置优先级

现有客户端允许本机手工服务器配置和本机固定密码优先于管理端隐藏配置。本方案第一阶段保留这一行为，避免扩大客户端改造范围。

Web 必须区分：

- 管理端期望设备组；
- 已下发策略版本；
- 客户端实际活动来源；
- 是否因本机手工配置而未使用设备组服务器配置。

如果后续要求“设备组强制管控，设备端不能覆盖”，应作为单独需求修改客户端优先级和 UI 权限，不能仅通过服务端字段调整实现。

## 12. 策略版本和下发

以下操作必须生成新的策略版本：

- 修改服务器配置内容或启用状态；
- 修改设备组服务器配置引用；
- 修改设备组无人值守状态；
- 修改、设置或清除设备组固定密码；
- 修改设备组 Root 执行器；
- 启用或停用设备组；
- 修改默认设备组；
- 调整设备所属组。

客户端通过后续管理心跳获取新策略。Web 中“保存成功”只表示服务端策略已发布，不能直接显示为客户端已应用；必须继续以设备上报的应用版本和运行状态作为实际结果。

## 13. 现有数据处理

本方案不兼容旧策略数据，也不提供数据转换工具。

实施新模型时：

1. 清空并按新结构重建策略相关数据，包括服务器配置、设备组和默认设备组关系。
2. 删除设备上的单设备服务器配置、无人值守和 Root 执行器旧值。
3. 管理员在新页面重新创建服务器配置和设备组，并重新设置固定密码。
4. 设备重新分组后获取新策略；未分组设备使用新设置的默认设备组。
5. 未设置默认设备组期间，设备按“无管理策略”处理：隐藏服务器配置关闭、无人值守关闭、管理端固定密码清空。

固定密码不能从旧密文自动带入，必须由管理员重新输入。初始化、数据库变更和日志均不得输出旧密码密文或任何密码明文。

## 14. 建议实施顺序

### 阶段一：服务端模型与策略解析

- 增加设备组策略字段和默认设备组字段。
- 调整密码加密保存位置。
- 将策略解析改成“已分组只用所属组；未分组才使用默认组；无可用组则无策略”。
- 保持客户端策略包结构不变。
- 补充策略解析、密码、停用处理和版本测试。

### 阶段二：Web 页面

- 精简服务器配置弹窗。
- 扩建设备组弹窗。
- 设备列表只保留分组操作。
- 增加完整的生效来源和客户端应用状态展示。
- 更新模拟 API 页面测试。

### 阶段三：旧入口与旧字段清理

- 删除单设备服务器配置、无人值守和全局服务器配置接口。
- 清理旧策略数据，不执行转换。
- 删除废弃类型、字段和解析分支。
- 更新 README、TODO 和实施记录。

### 阶段四：联调验收

- 部署管理端和受管 Android 客户端。
- 验证设备切组后的下一次心跳策略。
- 验证服务器重连、无人值守启停、密码设置和清除。
- 验证离线设备重新上线后的完整策略恢复。
- 验证本机手工配置优先时的 Web 状态提示。

## 15. 验收标准

实现完成后应满足：

- 管理员只通过设备组即可决定设备的服务器配置、无人值守和固定密码。
- 同一服务器配置可以被多个设备组复用，各组密码互不影响。
- 设备列表不再提供三个互相独立的策略编辑入口。
- 生效策略不会逐字段混合不同来源。
- 关闭无人值守后，管理端固定密码不再下发给客户端。
- 固定密码查询、日志和审计均不泄露明文或密文。
- 每次策略变化都有新版本，Web 能区分“已发布”和“客户端已应用”。
- 只有未分组设备使用默认组；已分组策略不可用时不静默回退，并在界面明确提示。
- 现有客户端无需改变策略包协议即可应用新模型生成的策略。
